# The build: what ships, the bundler, and the vendored binary

Everything the toolchain demands and nothing the game does: the five kinds of
file allowed into a tree with no authored assets, the one binary that ships and
why it is never named by path, and the two ways Vite's dependency optimizer has
already broken a running page. Split out of [`CLAUDE.md`](../CLAUDE.md), which
keeps the summary; this file is the contract for `vite.config.ts`, for
`package.json`'s generator scripts, and for anything reaching into
`@babylonjs/*`.

Nothing here is about how the game plays. It is here because every rule in it
was learned by losing a working build, and because none of it belongs to a
subsystem — a shader that stops compiling because of an import in an unrelated
file is not the renderer's contract to carry.

## What is allowed into the tree

**Zero model files, and SEVENTEEN audio files — one report per weapon in the
kit, the cupola gun all three hulls mount, the shoulder tube the third slot
carries, the two halves of the player's own magazine change, the four beats of
a bolt cycle and the two blasts, and nothing else in the game is recorded at
all** — every mesh is built from primitives at runtime (Babylon's, or for the
world kit and the scatter props the copies of them in `src/geometry/`), and every sound
is synthesized WebAudio (`src/core/Sfx.ts`) but for those seventeen. Do not add
asset files unless explicitly asked. Five exceptions, none authored by hand but
the fifth, each with a generator in `package.json`:

- `public/icons/` — generated, committed, regenerated by `npm run icons`.
- Havok's `.wasm` — vendored; see below on why it is never named by path.
- `textures/water-foam.png` (44 KB) — generated by `npm run textures` and
  imported by `WaterSystem` with Vite's `?url`. The one place the "everything is
  procedural" rule is bought out, because the mask is sampled per pixel and a
  canvas-generated equivalent would have to be rebuilt on every map install.

  **It used to be two, and losing the second one is worth reading as a warning
  about the first.** `water-normal.png` was a 512px tiling normal map the water
  surface was built from in three scrolled, rotated, mutually-warped layers, and
  every one of those adjectives was a defence against the same thing: a lattice
  sampled across a plane the size of a valley is a lattice you can see. It was
  visible anyway — as cloudy directionless mottling, which is what fBm is and is
  not what water is — and the fix was not a better image but no image: the
  surface is summed from directional wave trains in the fragment shader, which
  has no tile to hide. An asset that exists because a shader could not do the
  job is worth re-testing whenever the shader changes; this one had been
  carrying four separate rules to make it survivable. The FOAM mask stays
  because it is doing what a texture is good at — breaking up a metre-wide band
  through a smoothstep, where a repeat is neither visible nor a problem.
- `shots/<map>.avif` (~2 MB, seven of them) — what the main menu stands on:
  a photograph of each map, taken by `npm run shots` from the vantage that
  map's row in `src/ui/mapShots.ts` states, and imported the same `?url` way.
  It bends nothing, because a picture of a procedural world is still not
  authored art — the script rebuilds it out of the tree, and the pose that
  produced it is committed beside it rather than lost in the pixels.

  **They are 3840x2160 because the menu never shows one at its own size**: it
  drifts the picture between 106% and 113%, so a 1080p shot was magnified even
  on a 1080p screen and by 2.3x on a 4K one, which read as blur. The page is
  still laid out at 1920x1080 and shot at a device ratio of 2, with the render
  scale pinned to 1 — the default answers a 2x display with 0.5, a 1080p
  frame stretched to 4K. **AVIF at 4:4:4, encoded by `sharp`, because the
  service worker precaches every file the build emits**: four times the pixels
  as a JPEG would be four times the bytes on every phone that installs the
  game, and a subsampled encode stores colour at half resolution, a smear along
  every ink line. Every browser that can boot this game decodes AVIF, so the
  format costs no reach the WebGPU gate has not already spent.

  **This generator alone needs a machine with a GPU and a display**, and that
  requirement arrived with WebGPU. A headless Chromium cannot present a WebGPU
  canvas at all — the first `getCurrentTexture()` destroys the device — so the
  script launches HEADED, through `scripts/browser.mjs`, and on a box with
  neither it fails as a timeout waiting for a map that cannot draw. The other
  two browser-driven scripts (`npm run collision`, `npm run parity`) read state
  back out of the page rather than photographing it, so they stay headless and
  need only the WebGPU flag that module also owns. **It is a requirement of the
  generator rather than of testing it**: a shot is one of the five exceptions
  precisely because it has a generator, so what that generator costs to run is
  part of the bargain and belongs written down here.

- `audio/` (72.3 KB shipped, seventeen sounds off thirteen masters) — one
  report per weapon in the kit, the hulls' mounted gun, the AT launcher, the two
  halves of a magazine change, the four beats of a bolt cycle and the two
  blasts, and **the only
  asset class here whose input is a recording rather than a script**. It passes
  the common test all the same: `npm run audio` is the generator
  (`scripts/encode-audio.mjs`), the encoded `.webm` is committed, and the master
  it was cut from is committed beside it in `audio/src/`. The CUT is a `trim` in
  `audio/manifest.json` rather than something baked into a binary, so the
  shipped file is reproducible from the repo and the decision is reviewable in a
  diff.

  **It owes one test the other four do not, because a recording cannot be
  rebuilt from source the way a mask or a photograph can: is the game still
  whole with the file deleted?** Here, yes — `Sfx` fetches fire-and-forget off
  `unlock` and a round fired before the decode lands, on a device where the
  fetch failed, or in a browser that cannot decode the container is the
  SYNTHESIZED report, with no caller told the difference. The synthesis is not a
  fallback kept alive for this asset's sake; it is what the game does, and the
  recording is laid over the top. **A sound that cannot make that claim does not
  belong in this pipeline**, whatever its size.

  **What it refuses is a LIBRARY, and that is a boundary rather than a pause.**
  Eight reports and one magazine change is the whole of it: no footstep, no
  impact, no ambience, and no second take of anything. The budget is the reason
  and it is counted in SECONDS of decoded mono rather than in bytes on disk —
  the ten together spend 2.45 of 44, where thirty one-shots would spend 9 and a
  single thirty-second ambient loop 30. `docs/audio.md` has that arithmetic; the
  short form is that guns are exactly what sampling is worth paying for,
  ambience is exactly what the synthesis is already good at, and what is
  expensive in between is a CATALOGUE rather than any one sound. The reload is
  the sound that tested that: two cuts off one master, no variants, the player's
  own rather than every body's, and `Sfx.reload` is its four synthesized clacks
  with the files deleted.

  Two gates hold it: `scripts/check-audio.mjs` on the front of `npm run build`
  refuses a master edited without re-encoding (which would ship the OLD sound
  under a diff that looks right), a total over the manifest's seconds budget,
  and a mismatch in either direction between the encoded files and what
  `src/core/samples.ts` imports. **`npm run audio` needs ffmpeg on PATH and the
  BUILD does not** — the same shape as the shots generator's GPU requirement
  below. See [`docs/audio.md`](audio.md).

The common shape of all five: a **generator** in `package.json`, its output
**committed**, and the input that produced it committed beside it. That is what
separates a generated asset from an authored one, and it is the test to apply to
a sixth if one is ever proposed — not the file's extension, and not its size.

**There is no rigged character asset in the tree**, and the rule is in
[`CLAUDE.md`](../CLAUDE.md) because it spans three subsystems rather than this
one. `GlbSoldier.ts`, `entities/soldier/` and `@babylonjs/loaders` were deleted
when first person retired them, and the death cam stands up a bot rig rather
than bringing them back. What belongs here is the bundle half of the argument:
the camera is inside the head, so there is no own-body to render, and the death
cam — the one thing left that shows a whole soldier close up — stands up a bot
rig instead, because four seconds of screen time is not worth megabytes in the
download. The bot rig is also already what the ragdoll's bone table is measured
against, so the GLB would have bought a second skeleton to keep in step as well
as the bytes.

## There is no WebGL fallback, and what that costs is reach

**There is no WebGL fallback engine in the tree and there must not be one.**
`main.ts` gates the boot on `navigator.gpu` AND an adapter, so a browser
without one gets a sentence instead of a black page; what that costs is reach,
and Firefox on Linux/macOS plus older Android and iOS no longer boot at all.
Both phones are PWA install targets, so this is a product fact, not a detail.

## Havok's `.wasm` is the one binary that ships

~2 MB, pulled in by `@babylonjs/havok` for the ragdolls and the glass. It is
never named by path: Havok's ESM glue resolves it against its own
`import.meta.url`, which Vite follows and emits as a content-hashed asset
versioned with the dependency. Do **not** also hand-place a copy in `public/` —
that ships and precaches 2 MB twice.

Content-hashing it against the dependency is the whole reason the path is left
alone. A hand-placed copy in `public/` is unhashed and unversioned, so a Havok
upgrade ships new glue against a stale binary, and the service worker — which
precaches by name — has no way to tell that the file under the same name is now
the wrong one. See [`pwa.md`](pwa.md) for why every other asset in the bundle is
content-hashed for exactly this reason.

**It is REQUIRED and there is no fallback.** The boot gate, and the full account
of what the optional version cost, are in [`deaths.md`](deaths.md).

## The two WASMs that must never ship, and are not in the bundle at all

Havok's is the one binary that ships. There are two more the ENGINE will fetch
at runtime if anything lets it, and they are the reason a shader language is a
build contract rather than a rendering detail: **glslang and twgsl, four files
off `cdn.babylonjs.com/v9.28.0/`** (the installed version, which Babylon
writes into the path itself) — `glslang/glslang.{js,wasm}` and
`twgsl/twgsl.{js,wasm}`. `WebGPUEngine` builds them lazily, inside
`prepareGlslangAndTintAsync`, the first time a shader reaching the backend is
GLSL rather than WGSL; it is how the WebGPU port compiled the tree's GLSL under
the new engine for five milestones before the sources were rewritten.

**Every shader in the tree is WGSL now, so a fetch is a regression and what it
costs is the offline promise.** They are not in the bundle, they are not
precached, and nothing in `sw.js` knows their names — so a build that quietly
made one shader GLSL again would go to the network on its first DRAW, on a
device that installed the app to a home screen precisely so it would not have
to. Nothing about it is visible on a developer's machine.

**Two gates watch for it and both are needed, because each is blind where the
other sees.** `plans/webgpu-ref/harness.mjs` aborts `**/*.babylonjs.com/**` on
every page it boots and records every request to it, and `assertNoTranspiler`
reads `engine._glslang` / `engine._tintWASM` after a sweep that really compiled
something. A route filter proves only what was REQUESTED and a shader nobody
compiled requests nothing; the engine state proves the stronger thing and is
silenced by the abort, since an aborted fetch leaves both fields null. `gate.mjs`
and `shaders.mjs` fail on both. `VERIFYING.md` has the measurements.

## `optimizeDeps.exclude` in `vite.config.ts` is load-bearing for DEV

The dep optimizer copies the glue into `node_modules/.vite/deps/` and leaves the
binary behind, so the URL 404s and the SPA fallback answers with `index.html`.
The error blames the wrong thing twice — an `application/wasm` MIME complaint,
then `expected magic word 00 61 73 6d, found 3c 21 64 6f` (`<!do`) — and no MIME
tuning fixes either. **A production build resolves the asset itself, so `vite
preview` works with or without the exclusion; testing only there will not catch
this.** Deployed nginx needs nothing (`application/wasm` is in its bundled
`mime.types`; the web app manifest is not, which is why only that has a block in
`docker/default.conf.template`).

Both halves of that are worth keeping in mind together: the failure is
**dev-only**, and its error message names a MIME type in a project where no MIME
type is wrong. Time has been lost tuning the server that was already correct.

## Never add a deep static import into `@babylonjs/core`

The same optimizer bites from the other side. A new subpath entry
(`@babylonjs/core/Shaders/...`) makes Vite re-optimize the dependency
*mid-session*, which rewrites the chunk files Babylon's OWN dynamic `import()`s
resolve against — and the ones a running page already holds then 404. It cost a
debugging session: the casualties were `glowMapGeneration.vertex` and
`default.vertex`, so the glow layer and every `StandardMaterial` in the game
silently lost their shaders and **everything that glows stopped glowing, with
nothing wrong in the renderer at all**. The dev server console names the missing
chunks; the browser only shows the symptom.

Confirmed by control: re-adding two such imports to a running server 404s a
dozen Babylon chunks, removing them is clean. A fresh start (or `rm -rf
node_modules/.vite`) re-optimizes cleanly and hides it, which is why this
survives a restart for whoever pulled the change but never reproduces for
whoever wrote it.

Anything needing a Babylon shader's source must **wait for Babylon to import
it** (`OutlineFog.applyWanted` is the worked example) rather than reach for it
directly.

**The WebGPU port ended with NONE of them rather than six, and the grass is the
worked example of how.** It used to deep-import `ShadersInclude/instances*` for
the GLSL includes its vertex stage pastes in; the WGSL twins would have been two
NEW subpaths, so `src/shaders/wgsl/includes.ts` registers our own
`celInstancesDeclaration` / `celInstancesVertex` instead. They are fifteen lines
mirroring `ShadersWGSL/ShadersInclude/instances{Declaration,Vertex}.js` minus
the branches this game never compiles, and the header names the file and the
version so an upgrade has something to diff. That is the shape any future need
for a Babylon include should take. The other pair, `ShadersInclude/bones*`, left
with the skinned cel variant — there is no rigged asset in the tree, so nothing
had called it for a long time.

**`scripts/check-deep-imports.mjs` is what keeps the count at zero**, and it runs
from `npm run build` beside the collision check. It is the only absolute rule in
the project that `tsc` cannot see: a subpath import compiles, typechecks and
reviews clean, and what it breaks is a session on somebody else's machine. The
gate matches an import STATEMENT rather than the string, so the several places
that argue about these paths in prose do not fail the build for naming them, and
it is scoped to `src/` and `main.ts`. `server/` was outside it because it
imported `NullEngine` by subpath on purpose; since `BABYLON_EXIT.md` X2.3 it
imports no Babylon at all, which is the next section's gate rather than this
one's. **An empty allow-list is the only kind that stays empty**, which is why
the gate went in on the milestone that emptied it rather than being left for
later.

The reason this one is stated as an absolute rather than as a caution: the
symptom appears in a subsystem that has nothing to do with the import, on a
machine that is not the one where the import was written, and it goes away on
its own the moment anyone looks hard enough to restart the server. There is no
version of "be careful with deep imports" that survives that.

## The authority and the simulation import no Babylon: `check-babylon-free.mjs`

**`scripts/check-babylon-free.mjs` runs from `npm run build` beside the
deep-import gate, and it is the other rule `tsc` cannot see** — a property of
the import GRAPH rather than of a file. Phase 2 of `BABYLON_EXIT.md` took the
simulation off the scene and the authority off its engine: every system that
decides an outcome holds its state on `src/math` and leaves its picture to a
view module (`CLAUDE.md`, "Ownership and wiring"), and `server/` builds its
world from the collision bake with no mesh, no scene and no `NullEngine`. The
way back is one innocent import — a simulation pulls in a helper that pulls in
a mesh builder — and nothing else would notice: it typechecks, it plays, and
`dist-server` quietly loads Babylon again.

It walks the VALUE imports from two kinds of root: every file in `server/`, and
every SIMULATION module, named one by one in its `SIMULATIONS` list (the left
column of X2.2's table — `Player` among them, a simulation the authority never
builds). **A new module that simulates, or a system split into a simulation and
a view, joins that list in the commit that makes it**; a view never does, and a
listed file that no longer exists fails rather than dropping out. Type-only
imports (`import type`, an all-`type` named list, and the `export … from`
twins) are skipped, because naming a Babylon type loads none of it — `GameMap`
still names `Mesh` for the client's fields. Re-exports and `import()` are
followed, a computed `import()` or an unresolvable relative specifier FAILS (the
gate would otherwise have a hole), and resolution takes a name as written, so
`src/math`'s `./vector.ts` style resolves. A failure prints the importing line
and the shortest chain from a root to it.

**It widens on a schedule, not on a whim** (`BABYLON_EXIT.md` rule 6): X3.2
adds `src/render/` and `src/math/` to its `DIRECTORIES`, naming
`src/math/babylon.ts` — the crossing X1.1 made — in `NOT_ROOTS`, which exempts a
file from being a root and never from being REACHED; X6.1 widens it to the
whole tree, the day the package goes.

## A Babylon upgrade owes geometry-check, math-check, sweep-check, then `npm run merge:hash`

**The map build used to lean on Babylon's INTERNALS in four places, none of
which failed loudly when an upgrade moved what it leaned on, and since
BABYLON_EXIT.md X1.4 it leans on none.** Each was a claim that it did exactly
what a Babylon routine does, minus a GPU upload or a mesh: a cached
`CreateBoxVertexData` cube scaled per box (gone with X1.2); a part MESH that
held `Geometry.delayLoadState` at NOTLOADED for one `applyToMesh`, relying on
how `setVerticesData` postpones a buffer and when `applyToMesh` skips
`_applyToMesh`; a hand-copied `bakeTransformIntoVertices` over that mesh's own
arrays; and a hand-copied `Mesh.MergeMeshes` that called
`VertexData._mergeCoroutine` — an underscore member, which nothing in Babylon's
semver covers. All three of the last went with X1.4, and so did the mesh they
served: the world's merges, its vertex bake and its palette run on our own
buffers, and the world becomes meshes once, at the end of the build.

**What is left is no internal at all, only public API**, in two places:

- **The one adapter** — `drawnMesh` (`src/world/parts.ts`), and `worldMeshes`
  through it: `VertexData.applyToMesh` on a fresh `Mesh`, and
  `Mesh.setVerticesData` to make a pane block's positions writable.
- **The colliders**, which are still `MeshBuilder.CreateBox` boxes merged by
  `Mesh.MergeMeshes` (`MapBuilder.clusterColliders`, `struts`). Nothing that
  moves or shoots reads them since BABYLON_EXIT.md X2.1 — the rays and the
  sweeps both answer off the `WorldBox`es — so on the client they are the
  editor's centre-screen pick's, which walks a mesh's submeshes. The server
  builds none since X2.3.

**And the copies, which an upgrade cannot move but can make WRONG.** The
geometry every model and every structure is built and merged from is ours
(`src/geometry/`: the primitive generators, `mergeTransformed`, the transform,
the bake, the normals — Babylon 9.28's, operation for operation), and so is the
math under every transform (`src/math/`). Two scripts compare each copy with
the INSTALLED Babylon: `scripts/geometry-check.mjs` (the generators, the merge
— it is now the only caller of `VertexData._mergeCoroutine` in the tree, as the
reference the copy is checked against — the transform and the normals), and
`scripts/math-check.mjs` (`Vector3`, `Quaternion`, `Matrix`: the compose,
decompose, multiply and Euler conversions `worldMatrixOf`, `detachPart` and
`flattenParts` are built from). **The body sweep is a third copy**:
`src/world/ellipsoidSweep.ts` is Babylon 9.28's `moveWithCollisions` — the
collider's triangle test, its response and the coordinator's retry loop —
ported operation for operation against each `WorldBox`'s twelve triangles
(Apache-2.0 notice in its header), and `scripts/sweep-check.mjs` holds it to
the BIT against the installed Babylon in its default `exact` mode (it builds
each map as the authority does, off the bake, and its Babylon reference scenes
on a `NullEngine` of its own, so it needs no browser).
After an upgrade a difference in any of the three means
Babylon changed under the copy, not that the map moved — and since the copy is
what Babylon 9.28 did, which version it should now follow is a decision, not a
fix.

**So an upgrade is three runs, in this order, on the same machine.** Take
`npm run merge:hash -- --out before.json` (and the same with `--editor`) on
the OLD version. Upgrade. Run `node scripts/geometry-check.mjs` and
`node scripts/math-check.mjs` and `node scripts/sweep-check.mjs` — the copies
against the new library — then
`npm run merge:hash -- --against before.json` (and `--editor`). A merge:hash
difference with all three checks clean is Babylon's own output changing under the
adapter or a collider.
